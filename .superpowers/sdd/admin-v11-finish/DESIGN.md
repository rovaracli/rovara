# Task 1: owner-controlled company spending-stop enrollment

Final M2 design, superseding the M1 proposal. Authority: original admin-console brief, REVIEW-M1.md (PROCEED WITH CHANGES), and the owner's decision that disabling requires fresh sign-in but no second owner. No Tasks 2–4 implementation.

## States, authority and existing behavior

Exactly four edges: disabled -> ready, ready -> enabled, ready -> disabled, enabled -> disabled. Same-state operations and direct disabled -> enabled refuse. Bootstrap and upgrades remain disabled; ready has the same monetary behavior as disabled in existing readers. Enabling/disable never rewrite accepted task windows, spendingStop, funding proofs or customer spending limits.

Only a current owner may read enrollment/reviews or write any edge. The browser-session gate precedes lookups. The store reads checked membership, developer-org pointer, open company and live sign-in identity; it combines budgetActorChecks(role owner) with readAllowedDomainActorConditions. Admin, project maintainer, member and auditor cannot manage enrollment, regardless of caller claims. Cross-company pointers and private review ids cannot reveal another company's data.

Order: current owner -> bounded JSON decoding and strict body schema -> owner-checked replay -> fresh sign-in for money changes -> revision/review checks. The canonical state is read to determine whether a disabled request actually turns enabled enforcement off. Enable and enabled -> disabled require the acting owner's stored live session, isFreshSignIn, non-future authTime, matching session/person, unexpired endsAt, no revocation and no sessionsEndedAt invalidation. Ready cancellation has no monetary effect and needs no REAUTH. There is never a second-owner approval requirement for disable. Native role, pointer, org, identity and session conditions fence each commit. Conditional failures map by native-key index: authority first (FORBIDDEN), session (REAUTH_REQUIRED), economic/policy/review (CHANGE_STALE). Refusals write nothing and emit no refusal audit.

## Routes and wire data

GET /v1/app/org/task-stop-policy/enrollment returns checked orgId, state, revision. ?fresh=1 additionally checks sign-in freshness and is used before the UI loads a review. POST .../cutover-review accepts only requestId and expectedRevision. PUT .../enrollment accepts requestId, expectedRevision and state; ready/enabled additionally require reviewId and expectedReviewDigest, forbidden for disabled. JSON is limited to 16 KiB. Request ids and server-generated review ids are UUIDs. Browser-safe schemas are in contracts/task-stop-enrollment.ts; UI schemas/code are behind the owner step's dynamic import. Shared route wiring stays small.

A review returns orgId, reviewId, digest, revision, complete:true, capturedAt, expiresAt and at most 25 task impacts. Impacts contain only taskId, project, phase, effective stop, approval cap, current cap and a fixed outcome. No titles, instructions, raw source rows, native conditions or upstream errors reach the browser. Project labels render through VisibleText.

## Readiness, inventory and bounds

Before any review, page the native project catalog and custom-agent directory consistently, and visit the immutable builtin registry. Every project needs migrated taskStopPolicy; every agent/builtin needs recognized inheritance or an explicit valid stop, checked identity and revision; seed receipts and the canonical ceiling must be valid even when no active task uses them. Missing/unreadable/unprepared data refuses without partial writes.

Deduplicated economic weight W = 2P + A + B <= 80 (projects, custom agents, builtins). A conservative fixed allowance of 14 actions covers policy, member, pointer, org, identity, session, guardrails, two seed receipts, model sources, review evidence, audit and receipt. Thus <=94 actions, below DynamoDB's 100; task/workspace rows add zero. Runtime checks additionally bound transaction bytes below 4 MiB and each Put below 400 KiB. Review <=128 KiB; <=100 active tasks, <=500 workspaces and <=100 pages per native enumeration. Excess returns TASK_STOP_REVIEW_TOO_LARGE with a fixed company-too-large-for-one-step-enable message. The exact weight bound, bound+1 and 101-task refusal cases are tested against actual transaction lengths.

Workspaces are discovered through the existing eventually consistent project index, resolved by native task pointers, strongly re-read and org-checked, and deduplicated. Malformed pointers/foreign task rows refuse; standalone setup workspaces without a pointer are not tasks. The report is explicitly an as-of preview. Index omissions cannot grant money: consistent canonical admission after enable applies the existing enabled branch. First project registration with a present non-enabled policy adds only an enrollment snapshot condition and no new Put; a concurrent cutover refuses and retry seeds inherit on the enabled path. Existing agent creation already writes inheritance.

## Task impacts and lazy interaction

Capture uses continueAdmissionIdentity(task), shared with real Continue: the saved approved/path limit, committed max, saved or disabled-era requestedRunLimitUsd, chain and testing bounds. Queued zero-stop work is refuse_next_admission. Every positive queued stop is new_window_at_stop: Continue opens a full new window at current key spend (R38), irrespective of settled spend. No TASK_SPENT read is needed. Running work retains its admitted window until next admission, when a new window applies. Exempt requires an already-admitted task.fundingProof deep-equal to its frozen recipe fundingProof; disabled-era own-source tasks have no proof and remain subject to stops. Customer limits remain independent. The shared calculator's ceiling remains an approval cap, not a clamp on an ordinary unapproved estimate.

Counts cover all <=100 tasks. Classification is sequential (concurrency 1), bounded by the native inventory limits. The wire lists at most 25, ordered refusal, new-window, running, exempt, then task id. truncated signals the bounded list. The private review row retains all task ids (<128 KiB checked), so newImpacts counts newly observed ids whose fresh outcome is either refusal or new-window, even beyond the displayed list. Native identity races, including sessionsEndedAt changed at commit, deliberately remain FORBIDDEN; the person must reload/sign in again. sessionsEndedAt invalidation already visible at request time is REAUTH_REQUIRED for both enable and disable.

GET and disable validate company identity/revision/enrollment only; disable preserves malformed money fields under a full-row condition. Full readiness still validates policy content. Ready registrations seed inheritance under the company snapshot condition. Disabled registration adds a condition (so is not literally byte-identical) but creates no PROJECT_AI row and ignores unrelated money edits. Readiness identifies the first checked project/agent requiring repair.

TaskStopEditor exposes the step only to owners and dynamically loads TaskStopEnforcement/API. Freshness preflight comes before capture. Show the as-of review first, then explicit mark-ready and enable actions; ready can refresh its review after reauthentication. Disable is owner-only, freshly authenticated and audited. Unknown/stale responses clear the review; access/scope changes discard late responses. Existing windows remain captured after either enable or disable. Bundle cap stays 256000 gzip bytes.
