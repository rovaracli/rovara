# Safe action consumer API

`packages/ui/src/safe-action.ts` owns the final-refusal list. Pass the actual write route (`/v1/app/...` or its `/v1/web/...` alias), the `ApiError`, and, for Merge, the saved press’s `pullCount` to `isFinalActionRefusal`. Match status **and** code. Never add a screen-local any-4xx rule.

The audited routes include Cloud’s exact requestId validation and missing-session replies for stop/close/take-over; Code’s other replies on those routes remain unknown. The other audited routes are session retry/send-back/accept-findings/answers, task answers, requirements/plan/design card decisions, and Merge. The helper includes distinguishable Cloud pre-forward validation/session/conflict errors and Code’s proven pre-commit owner-round, answer-round, admission and document-gate refusals. A first Code HTTP 4xx can follow its own commit: generic owner/answer CONFIG_INVALID and TASK_NOT_FOUND stay UNKNOWN. On send-back and accept-findings, **every 409 IDEMPOTENCY_CONFLICT stays UNKNOWN/HELD**, including `People changed; refresh the task and try again` after the move. There is no message matching for this code on these two routes; the own re-read decides what applied. Retry and Answers keep their existing final tuple. Cloud validation with that same 400 code unlocks only on its exact, route-bound validation sentences. Retry NOT_FOUND/TASK_ACCESS_DENIED also stay UNKNOWN, as do the FORBIDDEN replies Cloud maps from a post-commit core Retry missing session or findings access reload; only the distinct Cloud owner-check sentence unlocks those FORBIDDEN cases. The five audited 402 budget admission tuples also apply to Retry: Code’s parity retry calls owner-round/admitRound before starting a run, so Cloud preserves those status/code/body replies and the browser shows Code’s words. All other step-Retry dispatch failures are mapped to 502 unknown, including conflicts and unrecognized 402 codes. Other paid-owner admission tuples belong only to send-back/accept-findings. Unreviewed routes or codes stay unknown. Audit evidence is in the lane’s `POST-FORWARD-AUDIT.md`; Code sources are `core/task-flow/{answer-request,owner-round,admission,retry,send-back,review-findings}.ts`, `core/decisions/{routes,performer,approval-gate}.ts`, `core-host/hosted-merge-routes.ts` and `core/merge/merge.ts`.

Read pending with `records.usePendingWithFence(subject, fence, read)`: when another tab removes a verified pending record, this tab installs its own fresh-read fence before notifying subscribers, then issues its own read. The same condition is checked synchronously inside the exclusive claim: observing storage removal before the browser delivers its event cannot permit a send. Keep the same fence across navigation and always perform a fresh own read on mounting a consumer. Merge retains its existing storage subscription until its own migration.

From `runActionPress.failed`, consumers may call `handleActionFailure` with the original entry, branded identity subject, records, section fence, message setter, an own `fencedRead` callback, and an identity read callback. It clears only that exact pending press on a proven refusal, surfaces the server’s own words, and fences use until a read issued after the refusal succeeds. Failed reads keep the fence; a later successful read recovers. Reads are fired without holding the action claim. CSRF_INVALID/CSRF_STALE take the separate pre-dispatch identity-refresh path; they are never treated as authority refusals. Unknown returns `"unknown"` and changes no pending record or read state. Preserve the original request identity across reload: a successful later read alone is never permission to discard that identity and resend an ambiguous action.

**202 `needs_confirmation` (including the take-over wire shape `status: "NEEDS_CONFIRMATION"`) is pending for decisions and take-over.** Task page and Work/Inbox consumers must retain the pending request identity; it is neither applied success nor a final refusal. The later own read determines whether the action applied.

Keep existing claim/persist/send/accepted-storage rules. Merge uses the classifier directly to retain its existing presentation and outcome: MERGE_NOT_READY stays unknown, as does CONFIG_INVALID for several PRs (or an unknown count). Code may have merged an earlier PR. Close TASK_NOT_FOUND and People/add CHANGE_STALE also stay unknown because Code can raise them after effects. 401 is always unknown here: Cloud already converts a dispatched write’s 401 to 503 without resending it. Every 5xx, 408, 429, network error, timeout or unreadable 2xx remains unknown.

While pending is unresolved, call `recordUnknownActionCheck(fence, entry)` once after each Check whose own reads still cannot resolve it. `useUnknownActionExit(fence, entry, taskHref)` returns `{ message, href }` after three such Checks **or** ten minutes from `entry.startedAt`. Render the message and the task’s app link **alongside the existing Check button**. This is presentation only: no resend, manual clear or disabled Check. Pass `undefined` when resolved. Use the existing identity/action fence, not a component-local fence. Counts survive navigation in that QueryClient; a reload uses the saved start time for the ten-minute exit. No storage schema or record kind changes.

Task page and Work/Inbox adopt this API after this helper lane merges; their lists are removed in their own lanes. New behavior has no feature switch.
